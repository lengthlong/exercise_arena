# 内核的写法

> 所有设计文字（含研究笔记与面向人的发布文档）先守本文件规则；`adr/` 与术语表（位置由配置 `context` 指定）的专属写法也在本文件。工作区专属的文件职责、方法与图的语法见本工作区 `design-writing`。
>
> 在设计工作区里以本文件为准：可借 `domain-modeling` 的术语表格式，但改设计文件须经落盘（`CLAUDE.md` 守则第 1 条），ADR 固定在根目录 `adr/`。

## 内容与语义保真

1. **先看用途与阶段，再定形式。** 按材料在当前设计阶段的用途评价，不拿终态规格苛求草稿。
2. **留白是合法状态。** 刻意不定的点显式标为留白，只写清位置与边界，不拿推测填补。
3. **术语一致。** 概念用配置术语表的首选词，流程词用 `CLAUDE.md` 定义；命令、路径、字段、接口与原始报错等机器字面量用代码格式保持原样；固定原文或反例不因风格改事实。
4. **改写保真。** 对照原文保留事实、数字、条件、例外、否定范围、因果关系与确定程度；改变上述含义属于新语义，须回讨论裁决。

## 设计与实现的分工

人与 agent 共用工作区地图，按材料用途与工作区实际确定设计、实现、测试与运行入口的职责和权威；不预设设计或实现永远优先，代码与测试也不默认替代契约。

1. **尚未实现，或行为需预先裁决时**：设计写清已裁的契约与关键行为规则。
2. **已有对应实现与测试时**：默认由设计写实现表达不了或跨多个部分的内容（概念定义、跨部分契约、外部可见的数据形状、校验条件与失败边界、不变式、理由与取舍、留白）；内部逐步执行细节写在实现与测试里，设计指向它，不复述（实现是 skill 正文这类散文时同样适用）。
3. **工作区定制**：本工作区要另一种权威分工时，在 `CLAUDE.md` 地图里写明。

## 面向人的表达与结构

面向人读的文档默认采用以下结构与行文方式；工作区本地 `design-writing` 补充领域职责与图的语法，另有约定的从其约定：

1. **按体裁裁剪。** 设计或方案总述采用下面第 2–5 条结构；会议材料、操作指南、进展报告、概念辨析等按各自用途裁剪；ADR、术语表按本文件专属节，研究笔记按其骨架。
2. **开篇导语定位。** 标题下用 1–3 行 `>` 引用块点明本文讲什么、怎么展开或当前成熟度（如初稿征求意见、基线范围），不写空泛寒暄。
3. **方案总述用「一句话 + 图 + 编号要点 + 概念表」。** 先交代背景、问题（必要时单列需求）与目标；方案总览先给**一句话核心命题**，配核心结构/交互图，再用**编号要点**（每条以 `**加粗结论句**` 打头，下挂 1–2 层短子项）拆解核心机制，配**术语/概念表**（条目多时按维度分组，列「维度 / 术语 / 含义」）。其后按需展开契约、讨论与参考。
4. **正文以层级要点与对称句组织。** 背景、问题、目标、方案细节与操作步骤优先用 2–3 层编号列表，一条讲一件事（操作说明先写前置条件再写动作，有歧义时写清执行者）；并列或对立设计用对称句式加粗词眼（如「长期：**稳定**的……；短期：**非稳定**的……」）。条件、原因与例外紧跟所限定的命题，既不堆砌多层嵌套的散文墙，也不切成五字一断的生硬电报句。
5. **对比必列表、取舍给选型。** 比较方案或区分易混概念时，按共同维度拉对照表（如优缺点、职责差异），表后紧跟明确的选型结论（含必要的短期/长期演进）；抽象概念配具体例子，图表配结论说明，不靠读者自己猜。
6. **讲清机制与数字，去源码考古与免责口癖。** 正文聚焦职责、边界、数据流与实测数字，不堆砌源码内部函数名或配置碎屑；**关联文档链接可随文给出，内部源码路径与函数定位收进文末「参考」**。按实际标注已完成、计划、提案或待确认，开放问题统一收进「讨论 / TODO」，不在段落间反复塞「此为推断、未实测」之类的防卫套话。

## 术语检查的边界

`./check.sh` 按 `.discuss_design.yaml` 的 `design` 范围扫描说明文字，命中 `terms` 中的无条件违例词即失败：

- **保护区**：围栏与缩进代码、行内代码、URL 及有效链接目标不扫描（链接显示文字仍扫描）。
- **豁免**：配置指定的术语表中以 `_Avoid_:` 或 `_Avoid_：` 起头的列表行自动豁免；固定引用或反例需保留违例词时，在同一行加 `<!-- design-terms-ignore: 理由 -->`（理由非空，仅豁免本行，代码内演示标记不豁免外部正文）。
- **失败保证**：文件枚举、规则扫描或处理器异常必须报错退出；句式、指代、技术正确性与改写保真由写作者对照实际稿核对。

## ADR（`adr/`）

1. **只写理由与取舍**，不复述模型与设计结构。
2. **三条标准全过才立档**：难以逆转、后人无背景会困惑、有真实取舍。
3. **结构精炼**：按信息组织短句短段，讲清背景、决定、理由与代价，有未决尾巴加「未决」段；理由可由 agent 取证论证提出（不冒充用户未表达的动机，新取舍改变已裁含义时回讨论）。
4. **文件名是一句结论**：`NNNN-<陈述句>.md`（如 `0001-step-binds-agent-directly.md`）；论证失效时按新裁决重写，名称失实时改名并同步引用。

## 术语表（配置项 `context`）

1. **只定义「是什么」**（一两句），不讲理由与实现细节。
2. **中英双名 + `_Avoid_`**：词条标题写 `English（中文）` 或 `中文（English）`，附 `_Avoid_` 列表收不用的同义词（最自然的译名若落在 `_Avoid_` 里则换用定义说法或解禁该词）。
3. **机械拦截**：无条件违例的 `_Avoid_` 词（出现即错）加入 `.discuss_design.yaml` 的 `terms`；特定语境才违例的词不加。

## 改完之后

1. **核对实际稿保真**：落盘后逐项对照原文核对事实、数字、条件、否定与机器字面量（标准路径的落盘前独立复审只评方案逻辑与核销计划，不替代实际稿自查）。
2. **同步影响面与配对侧**：术语或文件名变更时同步非冻结文件引用；改动落在地图配对的任一边时，同读另一边核对行为、契约与数字（实现偏离已定设计且在授权内直接修；设计过时或改裁决回讨论；超授权问用户）。
3. **跑 `./check.sh`**，退出码 0 才通过。
