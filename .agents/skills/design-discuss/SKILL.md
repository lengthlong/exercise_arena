# design-discuss

凡产出证据、选项或裁决的工作都按下面八步走；触发条件看产出，不看动了哪些文件。免走情形按 `CLAUDE.md` 守则第 1 条，包括不产生裁决的机械改动、适用的用户直接指示、已有授权内的实现落实与按已裁约定的日常运行；第 5 步派出的只读复审者也不另开讨论。产生新的设计决定仍按八步走，不以实现或运行的名义扩大已有授权。

地图、守则与词在 `CLAUDE.md`（托管块与它之后的地图）。写或复审设计文字先读 [WRITING.md](./WRITING.md) 的共守规则；ADR 与术语表按该文件，其余再读本工作区的 `design-writing`。`CLAUDE.md` 守则第 1 条的闸门在第 6 步打开。

## 八步

1. **建讨论文件** `discuss/NNNN-<topic>.md`：目的、输入、登记表。目的写明本轮具体产物与完成标准，区分总体设计目标与本轮交付；已经由用户明确的部分直接记录，不重复询问。「输入」只查同主题的未完成讨论，列在这里。编号是时序，文件名要看得出讨论及裁决的先后。处于只读模式（如 plan mode）时，先请用户切换，不先在对话里提问。
   完成：文件已存在，状态 `讨论中`；本轮交付与完成标准已写明，未定项有清楚的位置。
2. **取证、写提议**，按依赖排序。
   先核实影响选择可行性的关键技术前提，说明来自文档、用户告知还是实测；无法核实标未知与影响，不把未知当确定理由。独立于未知的部分可继续。需要承载已裁结果时，优先在已选权威文件里保存；可以经核销确认后落盘有留白的设计或 skill 草稿，不声称已可运行。延后产物说明实际未决依赖，不能只以整体方案未定或本轮叫定义工作区为由。
   完成：每条证据说得出来源。
3. **逐题问、逐题裁**，问法见「和用户协作」。正文逐题记录证据、选项与裁决，含被推翻的裁决；每次裁决、改裁、追加题都更新登记表。
   收到明确裁决后，核对登记表，主动继续下一道有证据、可裁的问题；需要取证就先取证，不等用户提醒、不先问是否继续。用户要求暂停、中止或另有安排时照办。范围变化时先核对已裁项的依赖，保留未受影响项，只把受影响项交用户重裁，登记表与正文同步；重开与分批按 `DISCUSSION-FILE.md`。默认本轮题目均有裁决或用户明确留白、暂缓后，再汇总核销。
   术语定案当轮写下完整定义与 `_Avoid_` 列表 —— 会话可能中断，它得完整到换个 session 也能照着落盘。明确无需修改的讨论到此关闭：状态改 `✅ 已完成（日期）` 并冻结，本地提交讨论文件及其研究文件，不走第 4–7 步。
   完成：登记表没有「待裁」行，暂缓与留白写明；就此关闭的，提交后用 `git show HEAD:discuss/<本轮文件>` 读出前几行，状态头是 `✅ 已完成（日期）`。
4. **起草核销表**：每条裁决一行，写明目标文件与改动；不改或暂缓的写明处置。
   核对本轮承诺交付：每项均有目标文件或用户明确的暂缓处置。核销表的实质约束对应已裁决定；标注新定不能代替裁决。有新的设计选择先回第 3 步，不在核销里隐含决定。
   完成：登记表上每条已裁都有一行，本轮承诺的交付物均有目标文件或明确的暂缓处置。
5. **独立复审**：
   - 按 [REVIEW-BRIEF.md](./REVIEW-BRIEF.md) 填好简报，派一个新上下文的 subagent，给它讨论文件与仓库，不给对话。复审对象是拟改内容与核销表，尚未写出的最终稿由第 7 步验证。
   - 主 agent 逐条核验发现，结果写进本轮讨论的复审一节。机械遗漏修进核销表并列出；改变设计的回到第 3 步，裁完就地重写核销表。
   - 重写后，主 agent 按简报自查重写过的行，结果写进复审一节，不自动再派。认为改动大的，写明理由，留到第 6 步问用户。用户要再派时，新派的 subagent 只评两版核销表之间的改动。
   完成：每条发现已核验，核销表已就地改写，重写过的行已自查。
6. **请用户确认**：把核销表贴进对话，状态改 `待落盘`；第 5 步认为改动大的，同时问用户要不要再派复审，要就回到第 5 步。用户确认完整核销表即为落盘授权，门槛覆盖本轮全部目标文件，术语也不例外。用户改表或追加题时回到第 3 步。
   完成：用户已确认。
7. **落盘与验证**：用户确认完整核销表后，按表改文件。
   - 落盘者按 `WRITING.md` 对照原文核对实际稿，记录保真结果；出现裁决之外的新语义时回到第 3 步。
   - 按 `WRITING.md` 与 `design-writing` 同步影响面。
   - 跑校验，记录自动检查与人工对照各自的结果。
   完成：`./check.sh` 退出码 0；改动过的图已经过启用集成的「图的校验」（没有启用或集成不提供时，按 `design-publish` 的能力退路跳过，并在第 8 步披露）；写回过目标的中枢已重抓、文件头已更新。
8. **核销与提交**：
   - 在讨论文件里逐行写实际改动与验证结果，写在一节二级标题下，标题去掉序号后以「核销」开头、且「核销」后面不紧跟「表」（如「## 六、核销（日期）」）。
   - 披露未验证项并取得用户接受；暂缓不代表问题已解决。
   - 状态改 `✅ 已完成（日期）` 并冻结。
   - 按 `CLAUDE.md` 守则第 4 条本地提交核销表列出的文件、本轮讨论文件及其研究文件，提交说明引用讨论编号。
   完成：每条裁决已落实或由用户明确不改、暂缓；commit 已建；提交后用 `git show HEAD:discuss/<本轮文件>` 读出前几行，状态头是 `✅ 已完成（日期）` —— 读已提交的内容，不凭记忆。

## 工具包的事

内核（本 skill、`design-research`、`design-publish`、`design-init`、内核检查与托管块的源）、集成 skill 与模板属于 discuss-design 工具包；本工作区提交的是所用版本的受管副本。讨论中发现问题出在它们身上（流程、检查、模板的写法）时：

- 该题在本轮的处置写「不改：属于工具包，去工具包仓开讨论」，不列进核销表；需要时把证据写清楚，方便到工具包仓里引用。
- 工具包只在工具包仓这个工作区里改，规则写在工具包仓的 `CLAUDE.md` 里。

## 讨论文件

- **登记表**放在状态头之后，每题一行：题（一句话）/ 状态（待裁 · 已裁 · 被取代 → 取代者）/ 现行裁决（一句话）/ 详见哪一节。现行结论以登记表为准；核销表复审后就地改写，不留初稿。
- **状态头**写成 `> 状态：**<词>（日期）**`，日期在加粗之内。只在暂停、分批落盘、中止、事后更正这四种情形，后面再接「—— 一句说明」（写法见 [DISCUSSION-FILE.md](./DISCUSSION-FILE.md)）；平时不接。进度（哪几题已裁、待裁哪题）只看登记表，不写进状态头。「事后更正」只用于已有核销记录、状态头却不是 ✅ 或 ⛔ 的讨论：改为 ✅（核销那天），说明写「状态头于 <日期> 更正，正文与核销未动」。词只有四个：`讨论中`（第 1–5 步、分批落盘期间、暂停）/ `待落盘`（第 6–7 步）/ `✅ 已完成（日期）` / `⛔ 已中止（日期）`。
- **结论落在哪**：要持续生效的结论按 `CLAUDE.md` 的地图落进设计文件，取舍的理由写进 ADR；无需修改的审阅结果或否决只留在讨论里。明确拒绝的方案连同理由记在讨论里，需要长期防止重提的写进相关 ADR。
- **少用的情形**：要分批落盘、暂停、恢复、中止、扫未完成的讨论、复审另一个 agent 的落盘，或由发布物改设计时，读 [DISCUSSION-FILE.md](./DISCUSSION-FILE.md)。

## 和用户协作

- **证据是你的，裁决是用户的。** 能查的事实自己核实；设计决定逐题交给用户，给出真实可行的选项、推荐与代价，不凑数量。
- **断言先核实，再写进裁决。** 核实不了就标未知；删规则要有行为证据，不能把「Agent 默认会做」当作已验证的事实。事实、推断与设计选择分别说明；推断写依据与确定程度，新增独立约束、文件权威或授权边界交用户裁，不藏在随之定下或核销表中；原裁决的机械落实不另造问题。ADR 的理由可由 agent 提出，不冒充用户未表达的动机；新取舍改变已裁含义时回到对应题。
- **追问解决实质未决问题。** 有影响当前决定或本轮交付的问题没说清时追问，说明要消除的不确定性与影响；用目的、理由、替代方案、反例、代价与后果检验。补充已经清楚就记录并继续；反问先回答，再判断是否有需裁的事项。能查的事实自己核实。独立新事项按依赖另立题，改变已裁前提时核对影响。以问题是否说清收束，不设固定追问次数。
- **一次只问一项可独立裁决的决定。** 能分别选择或分别改裁的事项拆题，各有登记行，按依赖先问最底层；必须一起成立的方案可作为一题，但写明依赖关系。问题锚在文档自身的证据上，假设性反例标明是检验。
- **对话里每题自足**：要用前面的结论就重述一句，不靠本轮编号回指；用平白的话，术语照用、不用自造缩写；给一个具体例子（取自本工作区的设计文件）；每个选项写明选了之后设计里什么变了、代价是什么；推荐必给，附一句理由。讨论文件里的题号照常用于追溯。
- **实质顾虑随时提**，写法仍要自足：发现矛盾、多条裁决叠加出的新风险、或被证伪的前提时，说明它从哪条证据来，提请用户重裁 —— 即使已裁、即使答复干脆。不自行推翻；用户要求收束时停止该分支。实质顾虑不受一次一题约束；无论答复是否干脆都须提出。核实不了的前提说明未知与影响，不以评论多少决定是否追问。

## 推荐时偏向什么

用户的决策取向。推荐时照此排序；较完整的方案仍列为选项并写明代价。

1. **简单优先。** 推荐最简、且不堵死以后扩展的选项。「简单」按概念更少、要建要维护的更少衡量；能推迟而不影响整体结构的推荐推迟 —— 不进设计，必要时记为留白。
2. **现成的能做就不重做。** 现成的工具、外部系统或已有的 skill 能处理的，不另建机制。
3. **概念从严。** 不为说明方便而造概念；过时或没用的设计从设计文件里删干净，不留「为什么不做」。
