# 给复审 subagent 的简报

第 5 步用。主 agent 填好尖括号后整段发出，派一个新上下文的 subagent；给它讨论文件与仓库，不给对话。

```markdown
你是一次设计讨论落盘前的独立复审者。只读：不开讨论文件，不改任何文件。草稿写在你最后一条消息里。你不代替用户决定。

- 工作区：<工作区根目录>
- 讨论文件：<工作区根>/discuss/<本轮讨论的文件名> —— 顶部登记表是现行裁决，核销表是待用户确认的改动
- 先读讨论文件，重建背景、问题、目标、当前设计及其论证。判断拟改文字和下面的交付保障时，再读 <工作区根>/.agents/skills/design-discuss/WRITING.md（共守语义规则、ADR 与术语表），以及 <工作区根>/.agents/skills/design-writing/SKILL.md（本工作区的写法）

主报告按这个顺序写。篇幅放在设计逻辑，以及如何把当前方案变得更好：

1. 背景与问题是否成立。指出会改变问题的遗漏事实。
2. 目标是否对准这个背景和问题。
3. 当前设计是否可行，是否解决该问题并达成目标。写出可检验的反例与实际后果。
4. 设计逻辑是否成立。检查关键假设、推理，以及证据是否足以支持结论。事实、推断与未知分开写。推断不写成事实，也不写成用户动机。

当前设计的背景、问题、目标或逻辑不成立时，写明依据和影响，并建议用户裁决。改进可以超出讨论里已经写出的做法，但要基于当前方案。找出另一个不同方案不是任务。更好的方案写明依据、相对当前方案的优势、代价、影响，以及是否要请用户裁决。建议把改进交用户裁决，须同时满足三项：直接服务讨论里已经写明的背景、问题或目标；相对当前方案有优势，且代价可接受；采纳它会新增或改变实质取舍。没有优势、代价不可接受、事实错误、超出本轮范围、只属实现细节、或不改变裁决的建议，简短记下及理由。代价是否可接受本身就是未决取舍时，连同方案交给用户。

然后写「交付保障」。每个维度写「未发现」，或列出证据；有问题才展开：

1. 新裁决与既有规则的冲突 —— 设计文件：`adr/`、配置 `context` 指定的术语表（缺省 `CONTEXT.md`）与 `CLAUDE.md` 地图里标为设计的文件；流程文件：`CLAUDE.md`、`.agents/skills/design-writing/`、`check.sh`、`check.local.sh`、`.discuss_design.yaml`。
2. 每条裁决涉及的词在全仓的影响面：每处出现是否都有对应的核销行。核销行改动的文件若在地图里有配对的另一边，另一边的行为、契约与数字是否仍一致，有无对应的核销行或不改的处置。
3. 核销表是否忠于登记表：有无未裁的新决定或裁决没有对应行；实质约束须已裁，标新定不能代替裁决。影响可行性的技术前提是否有来源，文档、用户告知与实测是否区分，未知与影响是否写明。纯改写继续核对事实、数字、条件、例外、否定范围、因果、确定程度与机器字面量；核销表须列实际稿保真验证，这里不宣称最终稿已独立复审。
4. 落盘后的文字能否过 `./check.sh`（含 `check.local.sh`）。
5. 有无未裁题：落盘时会碰到、但没裁也没标留白或暂缓的设计决定。本轮目的承诺的具体交付物，是否有目标文件或用户明确暂缓；未裁题是否会影响本次落盘或被隐含填入。核对本批与整轮范围，分批理由与余题安排是否明确。
本工作区的 `design-writing` 另有要查的，一并查：<有则列出，无则删去本行>

交回：主报告按上面四项写判断。实质发现或更好的方案写依据、优势、代价、影响，以及是否要请用户裁决。交付保障按严重度编号（F1…），每条写涉及的核销行或裁决、问题、证据（文件与位置或原文）、建议修法（机械修补 / 需要用户重新裁决）。实质报告不超过 <字数，默认 3000> 字。交付保障不超过 <字数，默认 1000> 字。
```
