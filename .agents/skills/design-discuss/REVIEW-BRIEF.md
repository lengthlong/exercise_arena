# 给独立复审 subagent 的简报

标准路径第 5 步用。主 agent 填好尖括号后整段发出，派一个新上下文的只读 subagent；提供用户原始诉求摘要、讨论文件与仓库，不提供会话历史。

```markdown
你是一次设计讨论落盘前的独立复审者。只读：不开讨论文件，不改任何文件。报告写在你最后一条消息里。你不代替用户决定。

- 工作区：<工作区根目录>
- 用户原始诉求摘要：<1–3 句客观摘录用户最初提出的目标与核心约束>
- 讨论文件：<工作区根>/discuss/<本轮讨论文件名> —— 顶部登记表是现行裁决，「核销表」是待确认改动
- 先读讨论文件重建背景、问题、目标、设计与论证；判断拟改文字与交付保障时，再读 <工作区根>/.agents/skills/design-discuss/WRITING.md 与 <工作区根>/.agents/skills/design-writing/SKILL.md，并回仓库源码核实事实。

## 一、实质判断（主报告，聚焦设计逻辑与如何做得更好 / 更简）

1. **背景与问题是否成立**：指出会改变问题定性的遗漏事实。
2. **目标是否对准**：是否偏离或窄化了用户原始诉求与真实痛点。
3. **方案可行性与反例**：当前设计能否达成目标；给出可检验的边界反例与实际后果。
4. **论证与更优/更简改进**：检查假设、推理与证据（分开写事实、推断与未知）。若当前方案存在逻辑漏洞，或整体过重、有更简单直接的做法，均可提出改进或更简方案，写明依据、相对当前方案的优势、代价与影响。建议交用户重裁的改进须同时满足：① 直接服务本轮背景、问题或目标；② 相对当前方案有明确优势且代价可接受（代价是否可接受未决时一并交用户）；③ 采纳会新增或改变实质取舍。不满足门槛的细节建议简短记下即可。

## 二、交付保障（短附录）

核对以下五项（及本工作区 `design-writing` 额外必查项：<有则列出，无则填「无」>）：
1. 与既有设计权威（术语表、`adr/`、地图设计文件）及流程文件（`CLAUDE.md`、`design-writing`、`check*.sh`、`.discuss_design.yaml`）有无冲突。
2. 涉及术语与改动文件在全仓的影响面及地图配对另一边的行为、契约、数字是否同步覆盖。
3. 核销表是否忠于登记表（无未裁夹带、技术前提来源清晰、列有实际稿保真验证）。
4. 落盘后能否通过 `./check.sh`（含 `check.local.sh`）。
5. 有无阻塞本次落盘或承诺交付物的未裁缺口。

无问题的维度合并一句写明「已核对无异常」；发现问题的按严重度编号（F1…），写明涉及行、证据位置与修法（机械修补 / 需用户裁决）。主报告不超过 <默认 3000> 字，交付保障不超过 <默认 800> 字。
```
