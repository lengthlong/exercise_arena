# design-publish

给人看的发布物（设计总述、演示稿……）放在外部平台上，叫**目标**。每个目标在本工作区有一个**中枢** `publish/<topic>.<ext>`：它是目标与本工作区设计之间的枢纽，四个方向都可以先发生。中枢不是设计权威，不被设计文件与 skill 引用（`CLAUDE.md` 守则第 2 条）。

本 skill 管同步模型与能力退路；对某个平台怎么发布、抓取、写回，由**集成** skill 提供。启用了哪些集成、它们的配置，写在 `.discuss_design.yaml` 的 `integrations`（集成名 → 配置）—— 启停集成后，用 `design-init` 的 link 按记下版本更新受管副本，再把配置与生成变化一起提交；要换工具包版本时另走 upgrade，先提交工作区改动。密钥类的 token 不写进任何仓库，放在平台工具自己的配置里。由用户按需发起；设计讨论不顺带改发布物。

新写或改写设计文字时，先读同版本 `design-discuss/WRITING.md` 的共守规则，再读本工作区 `design-writing`。按集成要求保留抓取的原文；允许改写的部分，对照原文核对实际稿。

## 中枢

- **格式由集成定**：中枢的扩展名与正文格式取决于目标（文档类通常是 Markdown）。
- **文件头三行**，写在正文之前的引用块里：
  - `> 目标：<链接>`
  - `> 与目标：<版本标记> · <日期>` —— 中枢与目标上次一致的位置。版本标记是什么（revision、修改时间、内容哈希）由集成说明。
  - `> 与设计：commit <X> · <日期>` —— 中枢与设计互相一致的基线 commit。
- **特殊取值**：尚未发布的，`目标` 与 `与目标` 两行写 `未发布`，发布后回填；不跟设计同步的，`与设计` 写 `不同步`；跟设计同步但没对照过的，写 `未对照`；新发布的记起草所依据的 commit。
- **正文**：初存时是从目标抓下来的原样，只做集成声明的「重抓后的改写」。之后可在中枢里改：新写或改写的文字按共守规则与 `design-writing` 写，已有正文不追溯、不规整；不存评论；同步状态不记，用时现算。

## 四个方向

同步前，先列出本次参与比较的中枢与设计文件，检查这些路径的暂存、未暂存与未跟踪改动（`git status --porcelain --untracked-files=all -- <本次路径>`）。有改动就列出路径并暂停，由用户先处理或明确授权提交；无关路径不要求干净，不自动 stash，不把用户原有编辑夹进同步输出提交。比较输入取已提交的内容，记清所依据的 commit。后续步骤产生的本次输出按每个方向的完成规则提交。

- **与目标双向，免讨论。** `与目标` 写 `未发布` 的，先发布、回填文件头，再谈同步。目标上先改的：按 `与目标` 记的版本抓取，与最新版比出改动，合进中枢。中枢上先改的：用定点写回改目标，不整篇覆盖（会冲掉评论）。两边都改过的：以 `与目标` 那一版为共同起点合并。写回后重抓、覆盖中枢正文（按集成的「重抓后的改写」），`与目标` 记新版本与日期。
- **`与设计` 是中枢与设计互相一致的那个 commit，前移它之前两个方向都要对照过。** 设计 → 中枢：核对基线与本次输入 commit 间的设计内容差异，把变更写进中枢，免讨论。中枢 → 设计：核对两者间的中枢内容差异，涉及设计的，开一轮讨论（取证前在状态头记基线）逐题裁，落盘改设计文件。`git log` 用于定位历史，是否有变更由内容比对决定，不以日志为空断言没有编辑。中枢没有改动时，设计 → 中枢写完即可前移 `与设计`；有改动时先写进设计变更也可以，但留到那轮讨论落盘时再前移。前移时记所依据的基线 commit（文件头写不进自己所在的 commit）与日期。
- `与设计：未对照` 的，先经一轮讨论做首次全文对照，之后才有起点；`与设计：不同步` 的不走上一项，改成同步也开一轮、同时做首次全文对照。每个方向完成后各自提交。
- **比对在本地做**（git 与文本比对），不是集成的操作。

## 集成要声明的操作

每个集成 skill 开头列出它提供哪些操作。

| 操作 | 必备 / 可选 | 做什么 |
|---|---|---|
| 发布 | 必备 | 在目标平台新建一份，返回链接 |
| 抓取当前 | 必备 | 取目标的最新正文 |
| 版本标记 | 必备 | 给出能判断「目标变了没有」的标记 |
| 按版本抓取 | 可选 | 取目标在某个版本标记时的正文 |
| 定点写回 | 可选 | 只改目标里变了的那几段 |
| 重抓后的改写 | 可选 | 把抓下来的正文改写成本工作区的写法（如图与引用的格式） |
| 图的校验 | 可选 | 确认设计文件里的图能被正确渲染 |

## 能力退路

集成缺某个可选操作时，照下表做，并在讨论的核销里写明走了哪条退路。

| 缺的操作 | 退路 |
|---|---|
| 按版本抓取 | 用 git 里最后一次更新 `与目标` 的那一版中枢作共同起点 |
| 定点写回 | 先把目标上的改动合回中枢；告诉用户整篇覆盖会丢掉评论与他人的排版，用户确认后整篇覆盖 |
| 重抓后的改写 | 不改写，原样存 |
| 图的校验 | 跳过校验，在核销里披露为未验证项 |

目标连整篇覆盖都不支持时怎么写回，尚未定：接入那样的集成时，在工具包里开一轮讨论定下这条退路。
