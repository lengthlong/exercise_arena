# design-verify

Run registered `verify/` entries for a feature slice or release candidate in one of two explicit modes—**Feature Verify (`scope: feature`)** or **Integration Verify (`scope: integration`)**—without adding a third regression mode. `model/verify/SPEC.md` holds stable acceptance policy (`OFFLINE` environments, substitutes, phase/cadence policy, external-write confirmations and exemptions); `verify/README.md` is the sole catalog of concrete entries, commands and tags (`journey/area`, `cost: automated | manual`, `cadence: always | on-touch`, `default phase: feature | integration | both`). Both `design-implement` and `design-verify` may author or maintain `verify/` entries within settled `model/verify/SPEC.md` and `journey/` boundaries. Acceptance writes only `verify/` (when adjusting cases) and `record/verify/`, and may use the temporary or `OFFLINE` environment defined by the entry.

## Modes

- **Feature Verify (`scope: feature`):** checks a changed feature's user-facing functions against journey success conditions in a fast, isolated or simulated `OFFLINE` environment.
- **Integration Verify (`scope: integration`):** checks the whole release candidate across accumulated changes since the last release for that target, including unaffected-journey regression and applicable catalog entries in `verify/README.md` (`cost: automated` defaults to `always`, `cost: manual` defaults to `on-touch`, overridable per entry via `cadence`). If a prod-only workspace's `model/verify/SPEC.md` explicitly declares no `OFFLINE` environment exists, run applicable local/simulated entries and mark prod-only boundaries `unverified` (zero `fail`).
- **Simple or single-feature releases:** when one pass already covers Integration Verify requirements (including lightweight manual `verify/README.md` walkthroughs), skip a separate `scope: feature` pass and write one `> scope: integration` record.

## Rules

1. Never list `./check.sh` or registered implementation tests as acceptance judgment rows in `record/verify/`.
2. **Strict write boundary:** `design-verify` may write ONLY `verify/` (including `verify/README.md` and entry files, within settled `model/verify/SPEC.md` and `journey/` boundaries) and `record/verify/`. Never modify `CLAUDE.md`, `journey/`, `model/`, `impl/` or `operate/`.
3. **Editing `verify/` directly:** When an entry is missing or needs adjustment, repair or recategorization without changing `impl/` or `operate/`, edit `verify/` directly instead of bouncing to `design-implement`. After editing `verify/`, run `./check.sh` and registered implementation tests (Rule 4—never counted as acceptance verdicts): if a failure lies in `verify/`, fix `verify/` and re-check; if fixing it requires editing `impl/` (including `impl/test/`), `operate/`, `CLAUDE.md`, `model/` or `journey/`, revert or leave uncommitted the incompatible `verify/` edit and route to `design-implement` (or `design-discuss`). Commit the passing `verify/` edit first, then record that commit as `> baseline:`.
4. Obtain separate user confirmation for steps that write external state, including `OFFLINE` environment deployment, real integrations, paid calls, shared environments or pushing records. Otherwise mark the boundary `unverified` and retain a local record.
5. **User-directed sizing and `fail`-only `in-progress`:** On any run (including `scope: integration`), the user may widen, narrow or skip specific cases. Mark unrun, simulated-only real boundaries, stale evidence or user-skipped cases `unverified` with the reason (e.g., `skipped by user: <reason>`), never `pass`. Keep `> status: in-progress` **only** when any judgment is `fail`; zero `fail` marks `completed`.

## Workflow

1. **Select mode, scope and upstream records:** Choose `scope: feature` or `scope: integration`, confirm the decided scope slice (or requested scenario/journey steps, noting undecided scope), and use a committed baseline.
   - For `scope: feature`, select the implementation record(s) for the changed feature.
   - For `scope: integration`, gather **all** implementation records in the baseline tree since the last release candidate for that target (treating `record/release/` and legacy `record/deliver/` as one combined prior-release history), or since the first commit.
   Include records from rewritten history (rebase or squash merge) and disclose ancestry differences. Under squash-merge workflows, run Feature Verify on the PR branch before squash merge and Integration Verify on the target/release branch after merge. Read the relevant journey success conditions, `model/verify/SPEC.md` and `verify/README.md`.
2. **Match baseline product tree and account for unrecorded product changes:** Match the baseline **product tree outside `record/` and `verify/`** to the `<end>` commit of an implementation record with passing registered tests (ignoring intermediate `record/` and `verify/` commits inside an implementation range); route unmatched product trees (including post-merge or squash-merged trees whose `<end>` no longer matches or is unavailable) to `design-implement` for a post-merge integration retest. Account for non-exempt commits modifying paths **outside `record/` and `verify/`** not covered by implementation records by mode (`verify/`-only commits are logged in `record/verify/` and covered by `> baseline:`, not listed as unrecorded product changes):
   - In `scope: feature`, list and cover only unrecorded product changes affecting that feature's scope (never pulling in commits covered by unselected implementation records or unrelated since-last-release commits).
   - In `scope: integration`, list and cover all remaining non-exempt commits outside `record/` and `verify/` since the last release for that target.
3. **Size the run from `verify/README.md`:**
   - In `scope: feature`, take the union of paired entries, affected journey steps from the selected implementation records, applicable `feature`/`both` entries in `verify/README.md`, and feature-scoped unrecorded product changes.
   - In `scope: integration`, apply `verify/README.md` catalog defaults (`cost: automated` → `always`; `cost: manual` → `on-touch` for boundaries touched since the last release; explicit `cadence` overrides `cost` default) across `integration`/`both` entries, combined with all since-last-release implementation records and unrecorded product changes.
   Present the default sizing basis so the user can widen, narrow or skip cases before running (noting any skip reason to record as `unverified`).
4. **Update `verify/` if needed (optional):** If cases are missing, inaccurate or need tag/script adjustments within the settled contract, edit `verify/`, verify with `./check.sh` and registered tests per Rule 3, commit the `verify/` change, and advance the working baseline to that commit.
5. **Prepare prerequisites and `OFFLINE` environment:** Trace environments, machines, credentials and dependencies to an operator journey, external responsibility or declared substitute. Stop on missing prerequisites unless the user explicitly skips the affected cases (record `unverified` with reason). Use the `operate/deploy/` deploy entry to place the candidate in an `OFFLINE` environment (QA, staging, integration or trial environment) as acceptance setup—never a release.
6. **Run entries:** Execute the selected `verify/` entries from `verify/README.md` (automated suites or lightweight manual walkthroughs) and record actual observations.
7. **Judge, record and route:** Judge every numbered user-perspective success condition as `pass`, `fail` or `unverified` (citing evidence or skip reason). Include required `> scope: feature` or `> scope: integration` using `assets/record.md`. Keep `> status: in-progress` **only** if any judgment is `fail`; set `completed` whenever zero `fail`. Commit on the acceptance branch:
   - On unreleased feedback-loop re-runs of the same slice or candidate, **update the existing acceptance record in place**: keep the `YYYYMMDD-<topic>.md` filename (updating the `> status:` date) and preserve existing judgment row numbers (append new judgments at the end), updating `> baseline:`, `## Upstream` (adding any new implementation record), judgments, evidence and concise round notes. Records freeze permanently globally once any completed release covers their work (or on `aborted`).
   Report the mode, baseline, scope, rationale, substitutes and unverified/user-skipped boundaries. Route `verify/`-only defects back into step 4 (fix in `verify/`, commit new baseline, rerun and update in place), product defects to `design-implement`, and contract/journey gaps to `design-discuss`. If `scope: feature` completed with zero `fail`, proceed to Integration Verify (`scope: integration`) before release or standalone `ONLINE` dark launch; if `scope: integration` completed with zero `fail` and release is wanted, proceed to `design-release` (which discloses `unverified` boundaries and checks any workspace deploy-contract release prerequisites). Otherwise take stock.
